# SharpChat API reference

The browser reaches the API under `/api` on the web app's origin (http://localhost:3000/api in Docker); nginx strips the prefix. Called directly, the API has no prefix (http://localhost:8080 for `api-1`).

Errors use [ProblemDetails](https://www.rfc-editor.org/rfc/rfc9457) with a machine-readable `code` (e.g. `email_taken`, `invalid_credentials`).

## Trying the API in Swagger

Swagger UI runs in Development at http://localhost:8080/swagger.

1. `POST /auth/register`, then `POST /auth/login`, and copy `accessToken` from the response.
2. Click **Authorize** and paste the token (without the `Bearer` prefix). It stays saved across page reloads.
3. Call any protected endpoint, e.g. `GET /users/me`. The access token lasts 15 minutes; log in again (or call `POST /auth/refresh`, which uses the cookie set by login) for a new one.

To look at the data directly: `docker compose exec postgres psql -U sharpchat -c 'select "Id", "UserName", "Email" from "Users";'`

## REST endpoints

| Method | Path | Auth | Description |
|---|---|---|---|
| POST | `/auth/register` | — | Create an account |
| POST | `/auth/login` | — | Returns an access token (15 min) and sets the refresh token (14 days) as an `HttpOnly` cookie |
| POST | `/auth/refresh` | Refresh cookie | New access token; the refresh cookie is rotated |
| POST | `/auth/logout` | Refresh cookie | Revokes the session and clears the cookie |
| GET | `/users/me` | Bearer | Current user |
| POST | `/conversations` | Bearer | Create a conversation (optionally with `memberUserNames`) |
| GET | `/conversations` | Bearer | Conversations I'm a member of |
| GET | `/conversations/{id}` | Bearer | Conversation details and members |
| POST | `/conversations/{id}/members` | Bearer (owner/admin) | Add a member by username |
| PATCH | `/conversations/{id}/members/{userId}` | Bearer (owner) | Change a member's role |
| DELETE | `/conversations/{id}/members/{userId}` | Bearer | Remove a member, or leave (own id) |
| GET | `/conversations/{id}/messages?before={cursor}&limit=50` | Bearer | Main timeline (thread replies excluded), newest page first (`nextCursor` loads older ones) |
| GET | `/conversations/{id}/messages/{messageId}` | Bearer | One message (e.g. to open a thread from a link) |
| GET | `/conversations/{id}/messages/{messageId}/replies?before={cursor}` | Bearer | Thread replies, same paging as the timeline |
| GET | `/conversations/{id}/changes?after={changeSeq}&limit=200` | Bearer | Everything that changed after a sync position (new messages, replies, edits, deletions), oldest first; `hasMore` when there is more |

Non-members get `404` for a conversation, so they can't tell whether it exists.

## Realtime (SignalR)

Hub: `/hubs/chat`. Authenticate with the access token (`accessTokenFactory` in the JS client, sent as the `access_token` query string).

| Direction | Name | Payload |
|---|---|---|
| Client → server | `SendMessage` | `{ conversationId, messageId, content, parentMessageId? }`. `messageId` is a GUID generated by the client, so retries are not duplicated; `parentMessageId` makes it a thread reply (one level only). Returns `{ data: message, error: null }` or `{ data: null, error: { code, message } }` |
| Client → server | `EditMessage` | `{ messageId, content }`. Author only |
| Client → server | `DeleteMessage` | `{ messageId }`. Author, admin or owner; the content is erased (soft delete) |
| Client → server | `MarkDelivered` / `MarkRead` | `{ conversationId, seq }`. Cumulative: "received / read everything up to `seq`" |
| Client → server | `Typing` | `{ conversationId, parentMessageId? }`. Fire and forget; send at most every few seconds |
| Client → server | `GetOnlineMembers` | `conversationId`. Returns the ids of the members who are online |
| Server → client | `MessageReceived` | The message, sent to every connection of every member (the sender included) |
| Server → client | `MessageUpdated` | A new version of a message: edited, deleted, or a parent whose reply count changed |
| Server → client | `PresenceChanged` | `{ userId, isOnline }`, sent to users who share a conversation with that user |
| Server → client | `UserTyping` | `{ conversationId, parentMessageId, userId, userName }`, sent to the other members |
| Server → client | `ReceiptUpdated` | `{ conversationId, userId, lastDeliveredSeq, lastReadSeq }`, sent to the authors of the affected messages and to the reader |

Every message carries `seq` (its position in the conversation) and `changeSeq` (bumped by every change). A client that remembers the highest `changeSeq` it has seen can always catch up with `/changes?after=`.

The refresh token never appears in a response body: it is the `__Secure-sharpchat-refresh` cookie (`HttpOnly`, `Secure`, `SameSite=Strict`, path `/auth`).

## Rate limits

Counters live in Redis, so they hold across instances. Defaults (section `RateLimiting` in configuration):

| Scope | Limit | Over the limit |
|---|---|---|
| `/auth/*` per client IP | 10 per minute | `429` with `Retry-After`, code `rate_limited` |
| Every other endpoint, per user (or IP when anonymous) | 300 per minute | `429` with `Retry-After`, code `rate_limited` |
| `SendMessage`, `EditMessage`, `DeleteMessage` per user | 30 per 10 seconds | hub error `rate_limited` |
| `Typing` per user | 2 per 4 seconds | dropped silently |

Health checks are never limited.

## Scaling

Docker Compose runs two API instances (`api-1`, `api-2`) behind nginx (`least_conn`). SignalR uses the Redis backplane, so a message sent through one instance reaches clients on the other. Clients connect with WebSockets only (`skipNegotiation`), so no sticky sessions are needed. In Development every response carries `X-SharpChat-Instance` with the instance that answered.
